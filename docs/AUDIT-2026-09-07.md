## ۳. شکاف‌ها — به ترتیب شدت

### 🔴 ۱. CSRF در ایمیج Docker پروداکشن **هر درخواست نوشتنی مرورگر را ۴۰۳ می‌کند**

`platform/src/proxy.ts:36`:

```ts
return new URL(origin).host === request.nextUrl.host;
```

`platform/Dockerfile` مقدار `ENV HOSTNAME="0.0.0.0"` را ست می‌کند، و در این
حالت `request.nextUrl.host` برابر `0.0.0.0:3000` می‌شود — مقداری که هیچ
`Origin` واقعیِ مرورگری هرگز با آن برابر نخواهد شد.

**اثبات (یک build واحد، فقط `HOSTNAME` متفاوت):**

| HOSTNAME | Origin ارسالی | نتیجه |
|---|---|---|
| `0.0.0.0` (مقدار Dockerfile) | `http://0.0.0.0:3000` | **200** |
| `0.0.0.0` (مقدار Dockerfile) | `http://127.0.0.1:3000` (همان Host درخواست) | **403** |
| `localhost` | `http://localhost:3001` | **200** |

یعنی در دیپلوی مستند (`docker-compose.prod.yml`) ورود، ثبت‌نام، بازیابی رمز،
۲FA و تمام CRUD پنل ادمین/مشتری از مرورگر ۴۰۳ می‌شوند؛ فقط کلاینت‌های بدون
هدر `Origin` (مثل curl یا همان پلاگین وردپرس) رد می‌شوند.

**علت اینکه تست قبلی پاس شده بود:** ROADMAP این مورد را «✅ `403` در برابر
`201`» ثبت کرده — آن تست احتمالاً زیر `next dev` اجرا شده که `HOSTNAME`
پیش‌فرضش `localhost` است.

**اصلاح پیشنهادی:** مقایسه با هدر `Host` درخواست (یا با allowlist مشتق از
`APP_URL`) به‌جای `request.nextUrl.host`.

### 🔴 ۲. CI عملاً وجود ندارد و همان یکی هم شکسته است

- `.github/workflows/docker-image.yml` دستور `docker build . --file Dockerfile`
  را در **ریشه‌ی ریپو** اجرا می‌کند، ولی در ریشه هیچ `Dockerfile` نیست
  (`ls Dockerfile` → *No such file or directory*). تنها Dockerfile در
  `platform/Dockerfile` است → این workflow همیشه fail می‌شود.
- `docs/ROADMAP.md` می‌گوید «CI روی PHP 8.1/8.2/8.3 ✅ `.github/workflows/qa.yml`»
  — چنین فایلی در ریپو وجود ندارد (`git ls-files | grep -c qa.yml` → `0`).

### 🔴 ۳. صفر تست خودکار در کل ریپو

`git ls-files | grep -Eic '(test|spec)\.(ts|tsx|js|php)$|__tests__|\.test\.'` → **`0`**
و در `platform/package.json` هیچ اسکریپت `test` تعریف نشده است.

در نتیجه هر ۳۰+ ردیف «✅ تست شده» در `docs/ROADMAP.md` دستی و
غیرقابل‌بازتولید است. باگ شماره‌ی ۱ بالا نمونه‌ی دقیق همین است: `typecheck`
و `lint` و `build` هر سه سبز بودند، ولی اپ در پروداکشن اصلاً لاگین نمی‌شد.

### 🟠 ۴. `npm run build` بدون متغیرهای env می‌شکند

`platform/src/lib/db/index.ts:12` در **scope ماژول** throw می‌کند:

```
Error: Failed to collect configuration for /api/admin/audit-log
  [cause]: Error: DATABASE_URL is not set. ...
      at module evaluation (src/lib/db/index.ts:12:9)
```

ترتیب مستند در ROADMAP (`npm run typecheck && npm run lint && npm run build`)
همین‌جا می‌شکند. خودِ `Dockerfile` با placeholderهای زمان build دورش زده است —
پس این بیشتر یک نقص robustness/مستندات است تا یک باگ پروداکشن.

### 🟠 ۵. `composer.lock` کامیت نشده

`git ls-files | grep -c composer.lock` → `0`. یعنی `composer install`
بازتولیدپذیر نیست و نسخه‌ی phpcs/WPCS بین توسعه‌دهنده‌ها و CI می‌تواند
فرق کند.

### 🟠 ۶. `getClientIp` بدون هدر forwarded مقدار `"unknown"` برمی‌گرداند

`platform/src/lib/http.ts:38-49`. در نتیجه همه‌ی کلاینت‌های مستقیم **یک
باکت مشترک** rate-limit دارند. اندازه‌گیری واقعی:

```
reg 1: 200 (ایمیل bulk1@…)   reg 2: 200 (ایمیل bulk2@…)
reg 3: 429 (ایمیل bulk3@…)   reg 4: 429 (ایمیل bulk4@…)
```

سقف `registerLimiter` برابر «۳ در ساعت به ازای هر IP» است، ولی چون IP همه
`unknown` بود، کاربر سوم با ایمیل کاملاً متفاوت بلاک شد. پشت nginx (که XFF
را ست می‌کند) درست کار می‌کند، ولی اگر اپ مستقیم در معرض اینترنت باشد،
rate-limit عملاً سراسری و قابل‌دورزدن است.

### 🟠 ۷. ادعای «تلاش پنجم → `423`» آنگونه که نوشته شده تکرار نمی‌شود

`loginLimiter` هم دقیقاً `points: 5` دارد (`src/lib/rate-limit.ts:43`) و
`consumeRateLimit` **قبل از** بررسی قفل صدا زده می‌شود
(`src/app/api/auth/login/route.ts:30` در برابر `:47`). پس از همان IP:

```
fail 1..5 → 401   درخواست ۶م → 429
```

`423` فقط وقتی دیده می‌شود که درخواست بعدی از باکت دیگری بیاید:

```
X-Forwarded-For: 198.51.100.10 + رمز درست → 423 «حساب شما … قفل شده است»
```

هر دو دفاع کار می‌کنند، ولی ترتیب مشاهده‌پذیر با آنچه در ROADMAP نوشته شده
فرق دارد.

### 🟠 ۸. `/admin` و `/dashboard` در این محیط قابل تأیید نبودند

هر دو با HTTP 500 برگشتند و علت در لاگ سرور:

```
⨯ Error: Failed query: select count(*) from "users"
  [cause]: Error: read ECONNRESET
```

این محدودیت هم‌زمانیِ PGlite است (چند query موازی در `Promise.all` روی یک
اتصال TCP) — همان چیزی که خودِ ROADMAP در بخش «یادداشت شفاف‌سازی محیط توسعه»
اشاره کرده. صفحاتی که query موازی ندارند (`/dashboard/licenses`،
`/dashboard/profile`، `/dashboard/security`) همگی **200** بودند.
**این مورد با Postgres واقعی تست نشده — باز است.**

### 🟡 ۹. موارد کوچک‌تر

- `sandbox/scripts/qa.sh` (تست فعال‌سازی واقعی روی WordPress) نیاز به Docker
  دارد که در این محیط نبود → ادعای ROADMAP تأیید/رد نشد.
- `spec/examples/` فقط **یک** فایل دارد (`store-health.json`)، در حالی که
  README به `spec/examples/*.json` (جمع) ارجاع می‌دهد.
- `phpcs.xml.dist` الگوی `*.stub` را exclude می‌کند، پس ۱۳ قالب
  `scaffold/*.stub` **هرگز مستقیم lint نمی‌شوند**؛ فقط غیرمستقیم و از طریق
  خروجی compose در `tools/build.php`. این طراحی آگاهانه است ولی یعنی
  `composer lint` به‌تنهایی بزرگ‌ترین بخش کد تولیدی را پوشش نمی‌دهد.

## ۵. ترتیب پیشنهادی برای بستن شکاف‌ها

1. اصلاح `src/proxy.ts` (مقایسه با هدر `Host` یا allowlist از `APP_URL`) +
   یک تست که سناریوی `HOSTNAME=0.0.0.0` را پوشش دهد.
2. یک workflow واقعی CI: `qa.yml` برای `composer lint` + `tools/build.php` روی

   `docker-image.yml` باید به `platform/Dockerfile` اشاره کند.
3. یک suite تست کوچک ولی واقعی: Vitest + `pg-mem`/PGlite برای سرویس‌های
   لایسنس و auth، و یک تست integration روی `proxy.ts`.
4. کامیت کردن `composer.lock`.
5. تبدیل اتصال DB به lazy (تابع `getDb()`) تا `next build` بدون env اجرا شود.
6. روشن‌کردن ترتیب rate-limit/lockout (یا مستندسازی رفتار واقعی).

## ۷. P0 — آنچه در همین نشست انجام و راستی‌آزمایی شد

### بسته شد

**۱. باگ CSRF (بند ۳.۱) اصلاح شد.** منطق مقایسه از `src/proxy.ts` به
`src/lib/origin.ts` منتقل شد و به‌جای `request.nextUrl.host` (که در حالت
`HOSTNAME=0.0.0.0` برابر `0.0.0.0:3000` است) از هدرهای `Host` و
`X-Forwarded-Host` استفاده می‌کند. راستی‌آزمایی روی build واقعی و سرور در حال
اجرا، با همان شکل پروداکشن:

| Host / X-Forwarded-Host | Origin | قبل | بعد |
|---|---|---|---|
| `shop.example.com` | `https://shop.example.com` | 403 | **200** |
| `shop.example.com` | `https://evil.example.net` | 403 | **403** |
| `127.0.0.1:3000` | `http://127.0.0.1:3000` | 403 | **200** |
| `app:3000` + XFH `shop.example.com` | `https://shop.example.com` | 403 | **200** |
| (بدون هدر Origin) | — | 200 | **200** |
| `/api/license/*` با Origin ناهمگون | `https://wp.test` | 200 | **200** (عمداً خارج از بررسی) |
| `/api/admin/*` با همان جفت ناهمگون | `https://wp.test` | 403 | **403** |

**۲. CI اضافه شد (بند ۳.۲).** `.github/workflows/qa.yml` با دو job: ماتریس
PHP 8.1/8.2/8.3 (`composer validate` → `composer lint` → build هر
`spec/examples/*.json` → assertion نبودِ `{{PLACEHOLDER}}` در ZIP → آپلود
artifact)، و job پلتفرم (`npm ci` → typecheck → lint → `npm test` → build با
placeholderهای زمان build → assertion وجود `.next/standalone/server.js`).
منطق shell این workflow عیناً به‌صورت محلی اجرا و سبز شد:

```
phpcs --standard=phpcs.xml.dist → exit 0
build هر spec نمونه            → Build succeeded.
assertion artefact/placeholder  → OK: build/store-health-1.0.0.zip (69K), ASSERT_FAIL=0
```

**۳. `docker-image.yml` اصلاح شد.** اکنون context برابر `platform/` و فایل
`platform/Dockerfile` است (قبلاً به `Dockerfile` ریشه اشاره می‌کرد که وجود
ندارد)، به‌علاوه‌ی یک مرحله‌ی smoke-boot که ایمیج را اجرا و `/api/health` را
می‌زند.

**۴. اولین suite تست خودکار (بند ۳.۳).** Vitest 4.1.11 + `vitest.config.mts`
+ اسکریپت `npm test`. **۵۳ تست در ۴ فایل، همه سبز:**

| فایل | تعداد | چه چیزی را پوشش می‌دهد |
|---|---|---|
| `origin.test.ts` | ۱۸ | ماتریس کامل CSRF، شامل دو تست REGRESSION برای همان `HOSTNAME=0.0.0.0` و fail-closed بودن |
| `totp.test.ts` | ۱۹ | وکتورهای رسمی RFC 4226 ضمیمه‌ی D (شمارنده‌ی ۰ تا ۹) + پنجره‌ی drift ±1 + فرمت `otpauth://` |
| `crypto.test.ts` | ۱۱ | round-trip، عدم قطعیت IV، رد دستکاری (GCM auth)، رد کلید اشتباه، `maskSecret` |
| `http.test.ts` | ۵ | اولویت `X-Real-IP`، آخرین hop از XFF، و fallback `"unknown"` (بند ۳.۶) به‌عنوان رفتار مستند |

**۵. یک نقص نهفته در `src/lib/crypto.ts` پیدا و اصلاح شد.**
`decryptSecret(encryptSecret(""))` استثنا می‌داد: چون بخش ciphertext برای
رشته‌ی خالی تهی است، شرط `!dataB64` آن را «payload نامعتبر» تلقی می‌کرد.
امروز قابل‌رسیدن نبود (هر دو فراخوان با `if (input.apiKey)` محافظت شده‌اند)،
ولی هر فراخوان آینده‌ای که `""` را رمز کند، ردیفی غیرقابل‌بازخوانی می‌ساخت.
اکنون تنها IV و auth tag الزامی‌اند و تعداد بخش‌ها باید دقیقاً ۳ باشد.

> نکته‌ی صادقانه: همین تست‌ها یک باگ در هلپر جدید خودم هم گرفتند —
> `new URL("app:3000")` با scheme `app:` پارس می‌شود و host تهی می‌دهد، پس
> `toHost()` باید protocol را چک کند. قبل از اصلاح، ۳ تست origin قرمز بود.

### باز ماند

- **`composer.lock` هنوز کامیت نشده (بند ۳.۵).** در این محیط قابل تولید نیست:
  نه باینری `composer` وجود دارد و نه `packagist.org` در دسترس است. ساخت
  دستی آن یعنی جعل hash — انجام نشد.
- **`qa.yml` و `docker-image.yml` روی رانر واقعی اجرا نشده‌اند.** منطق shell
  آن‌ها محلی تست شد، ولی `composer validate`/`composer install`، رفتار
  `setup-php` و `docker build` در این sandbox قابل اجرا نبودند.
- **`/admin` و `/dashboard` همچنان با PGlite خطای ۵۰۰ می‌دهند** (بند ۳.۸) —
  تغییری نکرد و به Postgres واقعی نیاز دارد.
- **ترتیب rate-limit/lockout (بند ۳.۷) و fallback `"unknown"` (بند ۳.۶)
  تغییر نکردند** — عمداً؛ تغییر کلید rate-limit یک تغییر رفتاری است و باید
  جداگانه تصمیم گرفته شود. رفتار فعلی با تست pin شد.
